# OrgAnchor Technical Decisions

Status: Active technical-decision summary; architecture decision records under `docs/adr/` remain the authoritative record for their individual decisions.

## Purpose

This document records the current technical choices for OrgAnchor and explains why each choice supports long-term organizational identity continuity.

The goal is not to make every reader a specialist. The goal is to make each choice auditable:

- What do we choose?
- What do we avoid for now?
- Why is this choice suitable?
- What can go wrong?
- How can it be replaced later?
- What is the v1 implementation level?
- Which primary sources support the decision?

## Decision Principles

OrgAnchor technical choices must follow these principles:

- The identity root is the organization root authority, not a platform, domain, chain, storage network, or single algorithm.
- The core verification path must remain small and independently testable.
- External systems are adapters. They can fail or be replaced without changing the identity model.
- Every publish operation must produce hashes and receipts.
- Every security-sensitive dependency must have a clear license and a replacement path.
- Unsupported algorithms, malformed statements, invalid signatures, and insufficient thresholds must fail closed.
- v1 may start with practical defaults, but file formats must support growth.

## TD-001: TypeScript and Node.js 24 LTS

Decision:

Use TypeScript and target Node.js 24 LTS.

Do not choose:

- Go or Rust for v1.
- Python for the main CLI.
- A browser-first implementation.

Why:

- OrgAnchor is CLI-first and npm-distributable.
- TypeScript gives strong types for schemas, statements, lockfiles, and provider adapters.
- Node has built-in crypto support for Ed25519, SHA-256, HTTP, DNS, TLS, and filesystem operations.
- Node 24 is Active LTS as of 2026-05-08, with end-of-life scheduled for 2028-04-30.

Risks:

- Node and npm dependency ecosystems require supply-chain discipline.
- Browser verification cannot blindly reuse all Node crypto APIs.

Replacement path:

- Keep core formats language-independent.
- Keep test vectors for canonicalization, hashing, signing, and verification so other languages can implement compatible verifiers later.

v1 implementation:

Real implementation.

References:

- Node.js release schedule: https://github.com/nodejs/Release
- Node.js crypto documentation: https://nodejs.org/api/crypto.html

## TD-002: npm and Plain TypeScript Build

Decision:

Use npm with `package-lock.json`. Build with `tsc` first.

Do not choose:

- pnpm workspaces in v1.
- A mandatory bundler for the CLI.
- A monorepo before the project actually needs one.

Why:

- npm is the lowest-friction default for a public Node CLI.
- A lockfile makes dependency state reproducible.
- `tsc` keeps the build transparent and avoids bundler-specific behavior around dynamic imports, JSON files, and crypto APIs.

Risks:

- Published package size may be larger than a bundled artifact.
- Later browser verification logic may need a separate build path.

Replacement path:

- Add `tsup`, Rollup, or another bundler only when there is a concrete packaging need.
- Add pnpm workspaces only if the project splits into CLI, core library, and verify-page package.

v1 implementation:

Real implementation.

## TD-003: Commander.js for CLI

Decision:

Use Commander.js for `organchor`.

Do not choose:

- A custom argument parser.
- A heavy interactive-first CLI framework.

Why:

- OrgAnchor needs predictable, scriptable commands.
- Commander is mature, focused, and suitable for nested commands like `archive arweave publish`.
- It keeps CLI logic separate from core verification logic.

Risks:

- Complex interactive setup flows may need additional prompt tooling later.

Replacement path:

- Keep command handlers independent of Commander so the parser can be replaced if necessary.

v1 implementation:

Real implementation.

- Commander.js repository: https://github.com/tj/commander.js

## TD-005: JSON Schema and Ajv

Decision:

Use JSON Schema with Ajv for statement, signature, root authority, migration, lockfile, and report validation.

Do not choose:

- TypeScript types alone as validation.
- Ad hoc field checks spread across commands.

Why:

- OrgAnchor artifacts are public JSON files. They need machine-readable schemas.
- Ajv supports modern JSON Schema drafts and is widely used in JavaScript environments.
- Schema validation lets external implementers validate OrgAnchor files without running the CLI.

Risks:

- JSON Schema cannot express every cross-file rule, such as "these signatures satisfy that threshold".
- Format validation can become inconsistent if custom validators are not documented.

Replacement path:

- Keep schemas in `src/schema/` and generated types in `src/types/`.
- Keep cross-file verification in `core/verify`.

v1 implementation:

Real implementation.

Reference:

- Ajv documentation: https://ajv.js.org/

## TD-006: Strict JSON Input Policy

Decision:

Signed artifacts must be strict JSON and must reject duplicate object member names before canonicalization.

Do not choose:

- Blindly trusting `JSON.parse` for adversarial signed artifacts.
- Allowing JSON5, comments, trailing commas, or duplicate keys.

Why:

- Signed JSON must have one unambiguous meaning.
- Duplicate JSON object names can make human review and machine verification disagree.
- RFC 8785 JCS constrains input to the I-JSON subset, which is appropriate for cryptographic operations.

Risks:

- JavaScript's built-in `JSON.parse` does not preserve enough information to detect duplicate keys after parsing.
- We need a small, well-tested strict parse layer or a parser library that can surface duplicate keys.

Replacement path:

- Wrap JSON loading behind `core/json.ts`.
- If the first parser choice is inadequate, replace it without touching command logic.
- Add fixtures with duplicate keys, unsafe numbers, malformed UTF-8, and valid RFC 8785 examples.

v1 implementation:

Real implementation. The exact parser package should be confirmed during the implementation spike.

References:

- RFC 8785: https://www.rfc-editor.org/rfc/rfc8785

## TD-007: RFC 8785 JSON Canonicalization

Decision:

Use RFC 8785 JSON Canonicalization Scheme for statement canonicalization.

Implementation default:

Use the `canonicalize` package behind a local wrapper, then test it against RFC and project fixtures.

Do not choose:

- Normal `JSON.stringify`.
- Sorting only top-level keys.
- Signing pretty-printed JSON bytes.
- Signing whatever bytes happen to be on disk.

Why:

- Hashing and signing require invariant input.
- RFC 8785 is designed for cryptographic operations over JSON while keeping the original data model as JSON.
- The `canonicalize` package is Apache-2.0 and explicitly implements RFC 8785.

Risks:

- Canonicalization libraries must be tested carefully around numbers, Unicode, arrays, and nested objects.
- RFC 8785 is informational, not an Internet Standards Track standard, so OrgAnchor must document its exact profile.

Replacement path:

- Keep all canonicalization behind `core/canonicalize.ts`.
- Maintain golden test vectors.
- A future implementation in another language can target the same RFC 8785 profile.

v1 implementation:

Real implementation.

References:

- RFC 8785: https://www.rfc-editor.org/rfc/rfc8785
- `canonicalize` repository: https://github.com/erdtman/canonicalize
- JCS test data repository: https://github.com/cyberphone/json-canonicalization

## TD-008: SHA-256 Hashing

Decision:

Use SHA-256 for statement and artifact hashes.

Format:

```text
sha256:<lowercase-hex>
```

Do not choose:

- MD5 or SHA-1.
- Provider-specific hashes as the only local reference.

Why:

- SHA-256 is mature, widely implemented, and available in Node crypto.
- It is suitable for comparing local and remote content.
- Prefixing with `sha256:` makes algorithm migration possible later.

Risks:

- The hash only proves content equality, not organizational authority.
- Hashes over JSON statements must be over canonical JSON bytes; hashes over uploaded files must be over raw file bytes.

Replacement path:

- Add new hash algorithms with explicit prefixes later, such as `sha512:` or a post-quantum-era recommendation if needed.

v1 implementation:

Real implementation.

## TD-009: Ed25519 Default Signature With Algorithm Agility

Decision:

Use Ed25519 as the v1 default signature algorithm, but require algorithm agility.

Do not choose:

- RSA.
- ECDSA as the main v1 default.
- Experimental post-quantum JavaScript signing as a required v1 dependency.
- A file format that assumes Ed25519 forever.

Why:

- Ed25519 is mature, compact, deterministic, and supported by Node crypto.
- OrgAnchor statements are public, so the key requirement is verifiable signatures, not encryption.
- The long-term identity concept is the root authority, not a single algorithm.

Risks:

- Ed25519 is not post-quantum secure.
- If enough root member private keys are leaked or derived in the future, attackers can sign false statements.

Replacement path:

- Every key and signature includes `algorithm`.
- Unsupported algorithms fail closed.
- Root authority can later include ML-DSA or SLH-DSA keys.
- Hybrid root authorities can require both classical and post-quantum signatures during migration.

v1 implementation:

Real implementation for Ed25519. Post-quantum support is not a v1 dependency.

References:

- Node.js crypto Ed25519 examples: https://nodejs.org/api/crypto.html
- OrgAnchor crypto policy: `docs/project/CRYPTO_POLICY.md`
- NIST PQC overview: https://www.nist.gov/cybersecurity-and-privacy/what-post-quantum-cryptography

## TD-010: Root Authority Set

Decision:

Model the identity root as a Root Authority Set:

```text
root public keys + threshold rule + traceable changes
```

Start with `1-of-1`, but support the schema shape for `m-of-n`.

Do not choose:

- A single root public key as the only possible identity root.
- Multiple people sharing the same private key.
- ENS, DNS, Arweave, IPFS, or any platform account as the root.

Why:

- Small organizations need a simple start.
- Mature organizations need distributed authority.
- Independent keys allow member changes and reduce shared-secret ambiguity.

Risks:

- Threshold rules are governance choices. Poor thresholds can create abuse or deadlock.
- v1 may implement only `1-of-1` signing while the schema is already multi-key capable.

Replacement path:

- `1-of-1` is just a special case of the same model.
- Add multi-sign workflows without changing the artifact model.

v1 implementation:

Real implementation for `1-of-1`; schema and signature file support multi-signature structure.

Reference:

- ADR 0001: `docs/adr/0001-root-authority-set.md`

## TD-011: Key Format

Decision:

Use OrgAnchor JSON files that wrap JWK key material.

Public root authority record:

```text
root-authority.json
```

Private key files:

```text
keys/<key-id>.private.json
```

Do not choose:

- Bare private key bytes on disk.
- A custom low-level key encoding.
- Requiring users to understand PEM, DER, or raw key formats in normal use.

Why:

- JWK is a standard JSON-friendly key representation.
- Node crypto can import and export JWK for Ed25519.
- Wrapping JWK lets OrgAnchor include `id`, `algorithm`, `created_at`, `usage`, and safety metadata.

Risks:

- Private JWK files are sensitive and must not be committed.
- Future post-quantum algorithms may not fit JWK equally well.

Replacement path:

- The wrapper can support `key_material.format` values such as `jwk`, `pem`, `raw`, or future algorithm-specific formats.

v1 implementation:

Real implementation.

## TD-012: Anchored and Self-Consistency Verification

Decision:

OrgAnchor verification must distinguish two levels:

```text
self-consistency verification
anchored verification
```

Self-consistency verification checks that a statement's signatures match the root authority record presented with it.

Anchored verification additionally checks that the root authority matches a known or expected root authority hash.

Do not choose:

- Treating a statement that embeds its own new root key as globally trustworthy.
- Hiding the root authority fingerprint from users.

Why:

- Any attacker can create a fake statement with their own key and sign it.
- The signature proves continuity only relative to a known root authority.
- Users and machines need to see which root authority was used.

Risks:

- New users may confuse "signature valid" with "organization trusted".

Replacement path:

- CLI output must label verification modes clearly.
- Add `--expected-authority-hash` and `--authority root-authority.json` options.
- Verify page should display the root authority fingerprint prominently.

v1 implementation:

Real implementation.

## TD-013: Signature File Format

Decision:

Use a detached JSON signature file with an array of signatures.

Do not choose:

- A raw base64 signature file.
- Embedding signatures inside the statement being signed.
- A format that allows only one signature.

Why:

- Detached signatures keep the statement readable and stable.
- Multiple signatures are required for future `m-of-n` root authority.
- JSON makes the signature metadata inspectable and archivable.

Risks:

- More verbose than a raw signature.
- Needs strict schema validation.

Replacement path:

- Add new signature algorithms by extending signature entries.
- Keep `version` and `algorithm` fields explicit.

v1 implementation:

Real implementation.

## TD-014: `organchor.lock.json`

Decision:

Use `organchor.lock.json` as a public, non-authoritative publish receipt ledger.

Do not choose:

- Treating the lockfile as a trust root.
- Storing private keys, wallets, seeds, or API tokens in the lockfile.
- Forcing statements to contain their own final IPFS CID or Arweave TX.

Why:

- Publishing creates receipts: hashes, CIDs, Arweave TX ids, provider names, timestamps, and verification results.
- These receipts must be reproducible and inspectable.
- Writing self-referential CID/TX values into the signed statement creates a recursive content-addressing problem.

Risks:

- Users may overtrust the lockfile.
- A stale lockfile may describe old publication state.

Replacement path:

- All lockfile entries point back to statement hashes.
- Verification always returns to statement signatures and root authority.

v1 implementation:

Real implementation.

## TD-015: Static Verify Page

Decision:

Generate a static `public/verify/index.html` and copy the relevant public artifacts into the same directory.

Do not choose:

- A hosted SaaS verification service.
- A framework-heavy single-page app in v1.
- A verify page that requires a backend.

Why:

- Static files are easy to publish on websites, IPFS, Arweave, and Onion services.
- A static page matches the disaster-recovery goal.
- It should be useful to both humans and machines.

Risks:

- Browser-based Ed25519 support and post-quantum support require careful compatibility work.
- A compromised website can alter the verify page's JavaScript.

Replacement path:

- v1 page displays artifacts, hashes, root authority fingerprint, and CLI verification instructions.
- Later add browser-side verification using a carefully reviewed library or Web Crypto where reliable.
- CLI remains the independent verifier.

v1 implementation:

Real implementation for static page generation. Browser cryptographic verification is an enhancement.

## TD-016: Evidence and Claims Manifests

Decision:

Add signed product claims and evidence manifests as part of Stage 3.

Use a hybrid carrier strategy:

```text
website /verify for discovery
IPFS for content-addressed mirroring
Arweave for critical long-term archives
object storage/CDN/Git releases for large artifacts
organchor.lock.json for publish receipts
```

Do not choose:

- Putting product claims, large PDFs, videos, or evidence bundles inside `official-endpoints.json`.
- Treating organization-signed claims as objectively proven facts.
- Requiring full JSON-LD, Verifiable Credentials, or C2PA processing in v1.
- Making AI agents scrape human-only web pages as the primary evidence interface.

Why:

- A real organization needs to prove more than where its official endpoints are.
- AI agents need structured, machine-readable claims and evidence relations.
- Large artifacts need external storage but must be hash-bound.
- Signed manifests let OrgAnchor prove publication, integrity, provenance metadata, and claim-evidence relationships.
- The hybrid carrier model avoids making websites, IPFS, Arweave, or object storage into a single point of failure.

Risks:

- Users may confuse "organization published this evidence" with "the product claim is objectively true".
- Evidence schemas can become too broad if v1 tries to model every domain.
- AI agents may over-rank first-party evidence unless issuer type and limitations are explicit.

Replacement path:

- Keep evidence schemas versioned.
- Keep claim/evidence manifests separate from endpoint statements.
- Use plain JSON and JSON Schema in v1.
- Add optional Schema.org, W3C PROV-O, W3C Verifiable Credentials, or C2PA compatibility later.
- Revisit carrier defaults as storage costs, AI-agent behavior, and provenance standards evolve.

v1 implementation:

Real implementation for signed claims/evidence manifests and artifact hash verification.

Reference:

- Evidence model: `docs/protocol/EVIDENCE_MODEL.md`
- ADR 0003: `docs/adr/0003-evidence-and-claims-layer.md`

## TD-017: IPFS via Local Kubo RPC, Remote Pinning Service API, and Pinata Upload

Decision:

Support local Kubo RPC first for IPFS publishing and verification. Support remote pin requests through an IPFS Pinning Service compatible API after the local path is stable. Also support Pinata directory upload because some providers require paid plans for "pin existing CID" while allowing direct upload on a free or lower-friction path.

Do not choose:

- Embedding a full IPFS node in OrgAnchor v1.
- Treating IPFS availability as guaranteed.
- Exposing the Kubo RPC API publicly.
- Hard-coding OrgAnchor to one pinning provider.
- Storing pinning API tokens in `organchor.lock.json`.
- Treating the default `public/verify` IPFS mirror as a large evidence repository.

Why:

- Kubo RPC is the official local node interface.
- It supports adding files/directories, pinning, and content retrieval.
- Local Kubo keeps the trust and operational model explicit.
- The IPFS Pinning Service API provides a common shape for external pinning providers.
- A remote pin improves availability but does not change the trust root.
- Provider-specific upload paths can be necessary when the common remote-pin API is paywalled or otherwise unavailable.

Risks:

- Users must have Kubo installed and running for real publish.
- IPFS CIDs prove content, not availability.
- Pinning providers are external services and may have accounts, quotas, monthly fees, policy limits, and outages.
- Remote pinning can keep content retrievable, but it must not be marketed as permanence.
- Large evidence artifacts should be independent evidence items with hashes and locations, not bundled into the default verification mirror.
- Pinning provider APIs vary.
- Provider-specific uploads may produce a different directory CID from local Kubo because import options and directory wrapping can differ. OrgAnchor records the directory hash and file hashes so the mirror remains auditable.

Replacement path:

- Define `IpfsPublisher` and `IpfsVerifier` interfaces.
- Add provider-specific helpers only where a common pinning API is insufficient.

v1 implementation:

Real implementation for Kubo, dry-run, generic remote pin requests, and Pinata directory upload.

References:

- Kubo RPC API: https://docs.ipfs.tech/reference/kubo/rpc/
- IPFS pinning services guide: https://docs.ipfs.tech/how-to/work-with-pinning-services/

## TD-018: Arweave via Manual Package First, Turbo Adapter Next

Decision:

Support Arweave as a first-class module, but start with:

```text
dry-run/manual upload package
```

Then use Turbo SDK as the first real upload adapter.

Do not choose:

- Blocking v1 on wallet setup.
- Hard-coding one upload provider into the core.
- Pretending Arweave availability or gateway access is guaranteed by OrgAnchor.
- Treating Arweave as the current authority layer or as a mutable storage backend.

Why:

- Arweave is useful for long-term archival of statements, signatures, and root authority records.
- Arweave's storage model is based on a one-time upfront payment and a storage endowment rather than ordinary subscription renewal.
- ar.io documentation presents Turbo as a recommended production-ready upload method with TypeScript support.
- A manual package allows users without credentials to still produce a verifiable upload bundle.
- Arweave is append-only. Corrections should be new signed statements that explicitly supersede earlier statements.
- OrgAnchor should not implement Arweave data-item signing itself when a mature SDK can handle it.

Risks:

- Turbo is still an external service.
- Turbo SDK must be installed in the environment that performs real uploads.
- Direct Arweave upload has more operational complexity.
- "Permanent storage" should not be marketed as "identity is permanently solved".
- Arweave's long-term durability depends on network economics, storage incentives, and continued protocol viability.
- Gateway URLs are access paths; gateways do not themselves guarantee permanence.
- Wrong, private, or non-final material should not be uploaded, because OrgAnchor must not rely on being able to edit or remove it later.

Replacement path:

- Define an `ArweavePublisher` interface.
- Keep receipts in `organchor.lock.json`.
- Support direct Arweave or other providers later.

v1 implementation:

Dry-run/manual package, pre-upload cost estimation, and Turbo SDK upload command are implemented. Real uploads require an Arweave/Turbo wallet and the Turbo SDK in the executing environment.

Reference:

- Arweave protocol site: https://www.arweave.com/
- Arweave lightpaper: https://arweave.org/files/arweave-lightpaper.pdf
- ar.io gateway boundaries: https://docs.arweave.net/learn/gateways
- ar.io upload documentation: https://docs.ar.io/build/upload/

## TD-019: OpenTimestamps / Bitcoin for Hash Time Anchors

Decision:

Add OpenTimestamps as a first-class hash timestamping module.

Use it for:

```text
root authority records
official endpoint statements
statement signatures
claims manifests
evidence manifests
Arweave manifests
```

Do not use it for:

- Storing content.
- Proving that a claim is true.
- Replacing OrgAnchor signatures.
- Replacing Arweave/IPFS/website retrieval paths.
- Making Bitcoin, OpenTimestamps calendars, or any Bitcoin API provider the identity root.

Why:

- OrgAnchor needs a strong public time anchor for key historical records.
- OpenTimestamps can prove that a file hash existed before a Bitcoin block time.
- It does not require an account, wallet, or project-specific payment for ordinary stamping through public calendar servers.
- It complements Arweave: Arweave stores retrievable historical content, while OpenTimestamps anchors hashes in Bitcoin time.

Risks:

- Public calendar servers are convenience infrastructure, not OrgAnchor trust roots.
- A newly stamped proof may remain pending until calendar data is anchored and upgraded.
- Bitcoin verification still requires access to a Bitcoin node or block API.
- The proof only binds a hash to time; it does not establish content truth or organization trustworthiness.

Replacement path:

- Add additional timestamping providers later.
- Support a self-run OpenTimestamps calendar if needed.
- Support direct Bitcoin node verification instead of public block APIs.

v1 implementation:

```text
anchor opentimestamps stamp
anchor opentimestamps upgrade
anchor opentimestamps verify
```

The implementation writes `.ots` proof files and records stamp/upgrade receipts in `organchor.lock.json`.

References:

- OpenTimestamps: https://opentimestamps.org/
- OpenTimestamps server: https://github.com/opentimestamps/opentimestamps-server
- Bitcoin developer reference: https://developer.bitcoin.org/reference/

## TD-020: Onion Module Generates and Verifies, It Does Not Run Tor

Decision:

OrgAnchor validates onion v3 addresses and generates Tor Hidden Service configuration snippets.

Do not choose:

- Running Tor inside OrgAnchor.
- Claiming OrgAnchor can prove onion service uptime.
- Supporting deprecated onion v2 addresses.

Why:

- Onion is a disaster-recovery access path, not an identity root.
- Tor has a clear v3 onion address format and setup process.
- Generating config and binding the onion address into a signed statement is within OrgAnchor's boundary.

Risks:

- A valid onion address can still be offline or controlled by the wrong operator.
- Onion service private keys require their own operational security.

Replacement path:

- Keep `onion validate` and `onion config generate` independent of other modules.
- Later add optional reachability checks through Tor tooling if users explicitly configure it.

v1 implementation:

Real implementation.

References:

- Tor onion address encoding: https://spec.torproject.org/rend-spec/encoding-onion-addresses.html
- Tor onion service setup: https://community.torproject.org/onion-services/setup/

## TD-021: Domain Audit With Automatic and Manual Checks

Decision:

Implement `domain audit` as a mixed automatic/manual report.

Automatic checks:

- DNSSEC indicators.
- SPF.
- DMARC.
- MX.
- CAA.
- HTTPS.
- Certificate expiry.
- `/.well-known/security.txt`.
- `/verify`.
- `official-endpoints.json`.
- `official-endpoints.json.sig`.
- RDAP registration data where available.

Manual checks:

- Registry Lock.
- Registrar account security.
- Auto-renewal.
- Billing status.
- Recovery contacts.

Do not choose:

- Pretending Registry Lock or auto-renewal can always be detected automatically.
- Treating domain security as the identity root.

Why:

- Domains remain the most common user entry point.
- Domain audit reduces real-world risk without confusing domain control with identity authority.
- Explicit manual checks are more honest than fake automation.

Risks:

- DNSSEC, RDAP, and certificate data vary by TLD and provider.
- Some registrars redact or omit useful data.

Replacement path:

- Add provider-specific audit plugins only when they improve accuracy.
- Keep report status values stable: `PASS`, `WARN`, `FAIL`, `MANUAL_CHECK_REQUIRED`.

v1 implementation:

Real implementation.

References:

- security.txt RFC 9116: https://www.rfc-editor.org/rfc/rfc9116
- ICANN RDAP overview: https://www.icann.org/rdap

## TD-022: ENS Inspect, Plan, and Verify

Decision:

Support ENS as an auxiliary name module:

```text
inspect
plan
verify
```

Do not choose:

- Making ENS an identity root.
- Requiring wallet write access in v1.
- Auto-applying ENS changes by default.

Why:

- ENS is useful for Web3 discovery and contenthash references.
- ENS text records can point to OrgAnchor metadata.
- ENS contenthash can point to IPFS or decentralized website content.
- Read and plan operations are safer than write operations for v1.

Risks:

- ENS records can expire, be transferred, or be misconfigured.
- Reading ENS requires Ethereum RPC access.
- contenthash handling needs careful encoding/decoding.

Implementation default:

- Use `viem` for ENS reads where supported.
- Use direct resolver contract calls for records not covered by a high-level helper.
- Generate a plan for suggested text records and contenthash values.

Replacement path:

- Keep ENS behind an `EnsClient` adapter.
- Add `ens apply` only after wallet config, transaction preview, and user confirmation are carefully designed.

v1 implementation:

Real implementation for offline plan and records snapshot verification. Live resolver reads require an Ethereum RPC adapter. Apply is optional later.

## TD-023: Provider Adapter Boundary

Decision:

All external systems use adapters:

- `ArweavePublisher`
- `IpfsPublisher`
- `EnsClient`
- `DomainAuditor`
- `OnionConfigGenerator`

Do not choose:

- Calling provider SDKs directly from CLI command files.
- Letting a provider receipt redefine OrgAnchor identity.

Why:

- External APIs change.
- Provider SDKs can have license, security, or availability issues.
- A clean adapter boundary lets us replace providers without rewriting identity logic.

Risks:

- Adapter interfaces can be overdesigned too early.

Replacement path:

- Start with narrow interfaces based on the v1 commands.
- Expand only when a second provider requires it.

v1 implementation:

Real implementation.

## TD-024: License and Dependency Policy

Decision:

Use Apache-2.0 for OrgAnchor. Core dependencies must be permissive and license-clear.

Allowed by default:

- MIT.
- Apache-2.0.
- BSD.
- ISC.

Avoid in core:

- GPL.
- AGPL.
- No license.
- Unclear license.
- Abandoned security-sensitive dependencies.

Do not choose:

- Copying code, docs, UI, or naming from adjacent identity projects.
- Adding a dependency merely because it is convenient.

Why:

- OrgAnchor is intended as an open-source infrastructure project.
- License clarity matters for organizational adoption.
- Security-sensitive tools need small dependency surfaces.

Risks:

- Transitive dependencies can introduce unexpected licenses.

Replacement path:

- Add dependency license checks in CI before public release.
- Keep security-sensitive dependencies wrapped and replaceable.

Policy now, CI enforcement before release.

## TD-027: Product Shape and Usability Surfaces

Decision:

Build OrgAnchor as several coordinated product surfaces:

```text
Core verification library
CLI
static adopting organization /verify page
future local-first OrgAnchor Studio
```

Do not choose:

- Defining OrgAnchor only as a CLI.
- Defining OrgAnchor as a central hosted website.
- Making an app, website, Studio, or hosted service into the identity root.
- Requiring users to depend on OrgAnchor-operated infrastructure for verification.

Why:

- The CLI is technically strong but not sufficient for ordinary organizational adoption.
- Real organizations need guided workflows, clear warnings, and readable reports.
- The public world needs a static `/verify` page and machine-readable artifacts.
- AI agents need structured JSON, not only human-facing pages.
- A future Studio can make the safe path easier without changing the trust model.

Risks:

- A convenient Studio could be mistaken for the authority itself.
- A hosted helper could accidentally turn into a central platform.
- UI convenience could hide the signed files and hashes users must be able to inspect.

Replacement path:

- Keep all product surfaces over the same open file formats.
- Keep CLI and independent verification functional without Studio.
- Keep Studio local-first unless there is a narrow, optional hosted use case.
- Keep private keys out of any hosted service by default.

v1 implementation:

Core, CLI, and static `/verify` page are part of the v1 path. Studio is a post-core usability surface and should be designed around the same artifacts.
